# 发布流程

公开下载与开发构建分开。CI 产物只是候选，需检查后发布 Release，不能直接把 artifact 链接当作长期下载入口。

## 首版分发

`v0.1.0-beta.1` 复用已验收的应用版本 0.1.0，不因公开下载渠道而重编译程序。新增的是公开仓库、文档和分发记录。Release 的 `PROVENANCE.json` 记录源码导入、原构建标识、运行时源码对应关系、文件哈希及限制；不声称安装文件来自本标签的一次全新编译或实现了可复现构建。

`v0.1.0-beta.2` 只新增 Windows NSIS `Setup.exe` 分发。使用 `Build Windows Installer` 工作流从明确的 `canonical` 提交构建安装器，固定并核对 beta.1 程序与运行时源码。工作流验证通过后，按下述草稿、校验和未登录下载流程发布；Mac 和便携 ZIP 继续链接 beta.1，不重新上传或覆盖。安装器附 `WINDOWS-INSTALLER-PROVENANCE.json` 与 `WINDOWS-INSTALLER-SHA256SUMS.txt`。

## 后续版本

1. 从 `canonical` 的明确完整提交构建，记录源清单和依赖锁文件。测试、审查通过后才能创建发布标签。
2. Mac 可使用手动 `Build macOS Internal Tryout` 工作流；Windows 在具备原生工具链的受控环境构建。不要把平台候选误写为均已验收。
3. 从最终 DMG/ZIP 取出程序，在对应架构检查启动、重启、窗口、原生接口、采集状态和文件完整性。真实工具样本与合成测试分开记录。
4. 分发白名单只包括应用、说明、许可证、构建信息和校验值；不得混入聊天、数据库、配置、凭证或开发机验收材料。
5. 在本地生成 `SHA256SUMS.txt` 和来源记录，逐项核对，创建 Release 草稿并上传附件。发布行为必须得到明确授权。
6. 检查草稿版本、标签、限制、下载入口和全部附件，再发布。未经实机验证的版本保持 pre-release；不要自动标成正式稳定版。
7. 使用未登录访问确认项目页、Release 和附件均可获取，下载后的哈希必须与本地发布清单一致。

已发布版本不覆盖附件或重写标签。发现问题时发新版本，或明确撤回并公告。更新 README 的下载入口，但保留旧版本和变更记录。

macOS 公证、Windows 签名、自动更新及其凭证需要单独授权和配置。仅建立 Releases 不会消除系统安全提示，也不会自动升级用户已安装的应用。
